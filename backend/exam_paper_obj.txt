Step 1 — Full Exam Creation Module: Teacher Experience & Functional Design

For your school platform, I would not design this as simply:

Teacher enters prompt → LLM generates questions → PDF

That will work for a demo, but for a production school platform you want:

Source → Content Understanding → Exam Blueprint → Question Generation → Validation → Teacher Review → Final Paper

The most important concept is the Exam Blueprint. The teacher should control exactly what kind of paper is produced.

1. What should the teacher be able to do?

Your Create Exam module can support several ways of giving content.

Source Type A — Upload PDF

Teacher can upload:

NCERT chapter PDF
School textbook PDF
Study material PDF
Teacher notes
Previous exam paper
Question bank
Worksheet

Example:

Upload Class_8_Science_Microorganisms.pdf

Teacher can also specify:

Pages: 20–35
Chapter: Microorganisms

Source Type B — Upload Image

This is very important for schools.

Teacher may upload:

Photograph of textbook pages
Scanned textbook
Handwritten notes
Blackboard notes
Diagram
Worksheet
Question bank photo

For example:

Teacher uploads:

Page1.jpg
Page2.jpg
Page3.jpg

The system should understand both:

Text

and

Visual information

such as:

diagrams

maps
tables

mathematical equations

Example:

"Create 5 questions using the diagram shown in this image."

2. Source Type C — Website / URL

Teacher can provide a URL.

Example:

https://ncert.nic.in/...

or a school website.

The system should retrieve the relevant webpage content.

Teacher could enter:

Source URL
Chapter: Crop Production
Generate questions only from this chapter.

This is especially useful for:

NCERT
CBSE resources
school learning portals
teacher-created webpages
educational websites

The platform should maintain the source URL with the generated questions so that each question can be traced back to its source.

3. Source Type D — Paste Text

Teacher can directly paste material.

Example:

Photosynthesis is the process by which green plants...

Then:

Generate a 20-mark quiz from this content.

Very easy and useful for teachers.

4. Source Type E — Existing Question Bank

This is actually one of the most valuable sources for production use.

Teacher can upload:

Previous exam papers
Question bank PDF
Excel/CSV
Word document
Existing questions

Then teacher can say:

Use previous papers only as a pattern reference.

OR

Select 10 questions from this question bank.

OR

Create new questions similar in difficulty to these questions.

This needs to be treated differently from textbook content because previous questions are examples, not necessarily the knowledge source.

5. Source Type F — Multiple Sources

A teacher should be able to combine sources.

For example:

Source 1:
NCERT PDF

Source 2:
Teacher notes

Source 3:
Previous question paper

Source 4:
Uploaded diagram

Then:

Generate the final paper from NCERT + teacher notes.

and:

Use previous paper only to understand question-pattern distribution.

This distinction is important.

This is the heart of your system.

Instead of asking the teacher to write a giant prompt, give them a proper UI/form.

8. Marks per Question

Example:

MCQ

Short Answer
4 × 2 = 8 marks

Long Answer
2 × 4 = 8 marks

1 × 5 = 5 marks

2 × 2 = 4 marks

This should be automatically validated.

The teacher should never accidentally create a 30-mark exam whose sections add up to 34 marks.

10. Difficulty Distribution

Teacher should control this.

Example:

Easy       30%
Medium     50%
Hard       20%

Or:

Medium     7 questions
Hard       3 questions

The generated paper should actually follow this distribution.

11. Cognitive / Bloom Level

For a production education platform, I would add this later, but design the module for it from the beginning.

Example:

Remember       20%
Understand     30%
Apply          30%
Analyze        20%

This is much better than simply saying:

"Make the exam difficult."

12. Chapter / Topic Distribution

This is another major requirement.

Suppose the teacher chooses:

Chapter 1: Crop Production       40%
Chapter 2: Microorganisms         30%
Chapter 3: Coal & Petroleum       30%

The system should ensure approximately that distribution.

Or the teacher can specify:

Topic                         Questions

Nutrition                     3
Reproduction                  4
Diseases                      3
Microorganisms                5

This becomes part of the exam blueprint.

13. Learning Objective / Concept Coverage

A strong exam generator should not simply generate random questions from a chapter.

For example, the source contains:

Concept A
Concept B
Concept C
Concept D
Concept E

Teacher may specify:

Concept A → 2 questions
Concept B → 3 questions
Concept C → 1 question
Concept D → 2 questions

The system then ensures topic coverage.

This becomes extremely useful for schools because teachers want:

"Did my exam cover the chapter properly?"

14. Include / Exclude Topics

Teacher should have controls like:

Include:
Photosynthesis
Respiration
Chlorophyll

Exclude:
Experiments
Historical background
Activity section

Or:

Generate only from pages 12–27.

This prevents unwanted questions.

15. Question Constraints

Teacher should be able to specify rules such as:

Do not repeat the same concept.

Do not repeat the same question from previous exam.

At least 2 application-based questions.

At least 1 diagram-based question.

No question should require knowledge outside the uploaded source.

Use simple English.

Do not ask questions about examples marked as optional.

These constraints are extremely important.

16. Source Strictness Mode

I strongly recommend giving the teacher a setting like:

Strict Source Mode

Questions must be answerable entirely from the selected source.

Useful for:

NCERT-based exams
school exams
chapter tests
Flexible Mode

Questions may require reasonable application of concepts contained in the source.

Useful for:

HOTS
competency-based exams
Olympiad-style preparation
Creative Mode

Use source concepts but allow broader question construction.

Useful for:

practice tests
quizzes
AI-generated worksheets
17. Previous Paper Pattern

Another powerful feature.

Teacher can upload:

Previous_Exam_2025.pdf

Then select:

Analyze pattern only.

The system can understand:

MCQ        30%
Short      30%
Long       20%
Case Study 20%

But it should not blindly copy questions.

Instead:

Generate a new paper following the same pattern.

This can become one of the biggest differentiators of your product.

18. Question Repetition Control

Teacher should have:

Avoid duplicate questions: ON
Avoid similar questions: ON
Compare against previous papers: ON

For example, these should probably be considered too similar:

What is photosynthesis?

and

Define photosynthesis.

Even though technically they are different sentences.

So your system should check semantic duplication, not just exact text duplication.

19. Question Dependency

A useful advanced option:

No question should reveal the answer to another question.

Example of bad exam:

Q1. Chlorophyll is responsible for ______.

Q7. Which pigment is responsible for photosynthesis?

These may unintentionally give away the answer.

Your system should detect such relationships.

20. Answer Length / Expected Response

For subjective questions, teacher can specify:

2 marks:
Answer expected: 2–3 sentences

5 marks:
Answer expected: 5–7 key points

The system should generate:

Question
Expected answer
Marking scheme
21. Answer Key

The output should include an answer key separately.

Example:

Q1 → B
Q2 → Photosynthesis
Q3 → 2 marks:
     • Point 1 = 1 mark
     • Point 2 = 1 mark

For long-answer questions:

Key points:
1. ...
2. ...
3. ...

This is very useful for teachers.

22. Marking Scheme / Rubric

For subjective exams:

Question: Explain photosynthesis. [5 marks]

Rubric:

Definition          1 mark
Role of sunlight    1 mark
Role of CO₂         1 mark
Role of chlorophyll 1 mark
Final equation      1 mark

This should be generated together with the exam.

28. Question Quality Checks

Before finalization, your module should check:

Factual correctness

Is the answer supported by the source?

Duplicate detection

Are two questions essentially the same?

Ambiguity detection

Does an MCQ have two possible correct answers?

Answer-option quality

Are distractors reasonable?

Marks alignment

Does question difficulty match marks?

Source grounding

Can the question be traced to source content?

Language

Grammar, spelling, readability.

Age appropriateness

Is the language appropriate for Class 5 vs Class 12?

Curriculum alignment

Does the question stay within selected syllabus?

These tell AI:

Step 2 — Technical Architecture
1. First, understand the roles

You don't need to think:

"Should I use GPT?"
"Should I use Gemini?"
"Should I use Claude?"
"Should I use an agent?"

Think in terms of jobs.

Your exam system has roughly these jobs:

1. Read documents/images
2. Extract/understand content
3. Store content
4. Retrieve relevant content
5. Understand exam requirements
6. Generate questions
7. Check questions
8. Check answers
9. Check blueprint
10. Let teacher review
11. Generate final paper

Different jobs can use different technologies.

3. Should you use one multimodal model?
My answer: No — not as the whole system.

A powerful multimodal model can read:

images
PDFs
text
diagrams
tables
screenshots

and reason over them. LangChain supports multimodal inputs such as images and PDF documents where the underlying model supports them.

So you absolutely should have a multimodal model available.

But I would not make it responsible for every operation.

Why?

Imagine 10,000 schools generating exams.

If every operation uses an expensive vision/reasoning model:

PDF reading
↓
chunking
↓
retrieval
↓
question generation
↓
validation
↓
answer checking

your cost will become unnecessarily high.

Instead:

Image → Vision model
PDF text → Parser
Retrieval → Embedding model
Question generation → Reasoning LLM
Simple validation → Python rules
Hard validation → LLM

This gives you much better scalability.

I would make this optional initially, but design for it.

For 100 schools and lots of books/question banks, this can become useful.

8. Model Type #5 — Validation/Judge Model

This is one of the most important pieces.

Don't trust the generation model to say:

"My own question is correct."

Instead:

Generator
    ↓
Question
    ↓
Validator

The validator checks:

✓ Source supported?
✓ Correct answer?
✓ Correct marks?
✓ Correct difficulty?
✓ Duplicate?
✓ Ambiguous?
✓ Outside syllabus?
✓ Answer actually answers question?
✓ Options have one correct answer?

For a high-quality production system, I prefer generation and validation as separate stages, and for important validation you can use a different model/deployment to reduce correlated errors.

Not necessarily a completely different vendor.

For example:

Generator model → strong model
Validator model → cheaper/independent model

And some checks shouldn't use an LLM at all.

9. Very important: Some validation should be Python, not AI

For example:

Teacher asks:

30 marks

Blueprint:

5 × 1 = 5
5 × 2 = 10
3 × 5 = 15

Python can calculate:

5 + 10 + 15 = 30

No LLM required.

Similarly:

Question count
Marks
Section numbering
Required fields
Percentage totals
Maximum/minimum constraints

should be deterministic.

So:

AI → semantic validation
Python → mathematical/schema validation

This is much more reliable.

For the core exam generator: NO.

This is a very important decision.

Your workflow is known in advance:

LangGraph explicitly distinguishes predetermined workflows from dynamic agents; LangGraph is designed for stateful orchestration, persistence and human-in-the-loop workflows.

So I would use:

LangGraph Workflow

"one giant Exam Agent"

21. Model Gateway — VERY IMPORTANT

This is where I would make the system scalable.

Don't write your entire application like:

openai_client.some_model(...)

everywhere.

Instead:

                Your Application
                       │
                       ▼
                 Model Gateway
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
     Provider A     Provider B     Provider C
      Model X        Model Y        Model Z

A gateway such as LiteLLM provides a unified interface to many model providers and supports routing, retries/fallbacks, and spending controls.

This means later you can change:

Vision Model A → Vision Model B
Generator Model A → Generator Model C

without redesigning your whole application.

39. The most important architectural principle

I would keep these five layers separate:

LAYER 1 — DATA
PDF / Image / URL / Question Bank

LAYER 2 — UNDERSTANDING
Parser / OCR / Vision / Extraction

LAYER 3 — KNOWLEDGE
Chunking / Embeddings / Vector DB / Retrieval

LAYER 4 — REASONING
LLM / Question generation / Validation

LAYER 5 — ORCHESTRATION
FastAPI / Queue / LangGraph / Human review

That makes the whole system replaceable.

For example, next year you can change:

Vision Model A
        ↓
Vision Model B

without changing:

Exam Router
PostgreSQL
LangGraph
Frontend
PDF generator

And you can change:

LLM A → LLM B

without changing your RAG system.

40. My final recommendation on "one model vs many"
Don't do this
One multimodal LLM
       ↓
Everything
Also don't do this
10 different LLMs
10 agents
20 services

That would be unnecessarily complicated.

Do this
              MODEL GATEWAY
                   │
        ┌──────────┼──────────┐
        ▼          ▼          ▼
     Vision      Generate   Validate
      Model       Model      Model
        │          │          │
        └──────────┼──────────┘
                   │
             Embedding Model

With:

LangChain → model/tool abstraction
LangGraph → deterministic AI workflow + state
RAG → source grounding
Python → deterministic validation
Vision → images/scans/diagrams
LLM → reasoning/generation
Vector DB → knowledge retrieval
Queue → asynchronous scaling
Gateway → model switching/fallback/cost control

This is the architecture I would choose for a school platform intended to scale to hundreds of schools, rather than building a single large agent.

One especially important point: the teacher's exam blueprint should become a formal typed object in your system, not just a prompt. The LLM should receive that blueprint plus retrieved source evidence and return strict structured question objects. That is what will let you reliably enforce marks, question counts, difficulty, topics, and eventually curriculum/Bloom-level coverage.

The next implementation layer

The natural next step is to convert this into an actual Eduverse backend design: exact FastAPI routers, Pydantic request/response schemas, database tables, services, LangGraph nodes/state, model interfaces, RAG pipeline, Redis jobs, and the exact lifecycle of POST /exams from upload → generation → teacher review → final PDF.
